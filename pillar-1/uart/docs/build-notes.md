# UART Build Notes

Running log of questions asked (and answered) while implementing this module, kept in my own words where it matters. Not a spec, not curriculum — just a memory aid for "wait, why did we decide that?"

---

## `mmio_register_bank.sv` — CTRL write/read

**Q: Should there be an `else` in `ctrl_write`'s `always_ff`, to avoid a latch?**
No — that framing borrows a rule from the wrong context. Missing-branch latch inference is a *combinational* logic concern (`always_comb`/`always @*`). `always_ff` is edge-triggered by construction, so it always synthesizes to a flip-flop regardless of whether every branch assigns something. No `else` just means "hold previous value on this edge," which is normal register behavior, not an inferred latch.
    
**Q: Should CTRL read be combinational or sequential — why is write sequential but read wants to be instant?**
Combinational read, sequential write — settled by what's live in the code (`assign rdata = ... ? ctrl_reg : 'x;`, with the sequential alternative commented out). The determinant isn't "are we touching a register," it's *who's creating new state vs. exposing existing state*. Write creates new state, so it must land in a flip-flop on a clock edge. Read doesn't create anything, it just selects what's already stored — making it sequential would add a needless cycle of latency that bus protocols like APB/AXI4-Lite don't want.

**Q: `tx_data` and `status` both need the FIFO, correct?**
Yes, and so does `rx_data`. TX_DATA write pushes onto `tx_fifo` (not a single-slot register); RX_DATA read pops from `rx_fifo`. STATUS is a mix: `TX_FIFO_EMPTY/FULL` and `RX_FIFO_EMPTY/FULL` are the FIFOs' own status outputs wired straight through; the rest of STATUS (`BREAK_DETECTED`, `NOISE_ERR`, `PARITY_ERR`, `FRAMING_ERR`, `RX_VALID`, `TX_BUSY`) comes from other blocks, not the FIFOs. `OVERRUN` is hybrid — set when a new RX byte arrives while `rx_fifo` is already full.

**Q: Verilator flags `address[31:4]` and `wdata[15:4]` as unused, `ctrl_reg[15:4]` as undriven — normal? Do unused bits become reserved automatically?**
`address[31:4]` unused is fine as-is — base-address validation is an upstream address decoder's job, this module only decodes its own local offset. `wdata[15:4]` will partially resolve once TX_DATA write lands (bits 9-15 stay genuinely unused regardless, nothing in the register map claims them). `ctrl_reg[15:4]` undriven is the real one: **no, reserved bits are not automatic.** That's a spec/documentation convention, not something RTL enforces on its own — an undriven slice of a declared output is `X` in sim and a dangling/tool-dependent net at synthesis. Needs an explicit driver to actually read as a defined `0`.

**Q: Tried `assign ctrl_reg[15:4] = '0;` right after the port list — got `%Error-BLKANDNBLK`, why?**
A continuous `assign` is a blocking-style combinational driver; `<=` in `always_ff` is nonblocking/procedural. Verilator doesn't support mixing those two styles on the same variable, even across non-overlapping bit ranges. Fix: drive it from *inside* the same `always_ff` block instead, as a nonblocking assignment, placed **unconditionally** (outside the `if (write_en...)`, not just after the `[1:0]` line inside it) — since there's no reset signal yet, an inside-the-if placement would leave those bits `X` until the first-ever CTRL write.

## `tx_fifo.sv` — first draft review

**Q: Does declaring `logic`/`int` inside a module (not a port) automatically make it a flip-flop?**
No. What determines it is entirely *how* the signal is assigned, not the declaration keyword. Procedural assignment (`<=`) inside a clocked block (`always_ff @(posedge clk)`) → real flip-flop, genuine persistence. Combinational assignment (`assign`, `always_comb`) → just wires/gates, zero storage, output is purely a function of current inputs.

**Q: So the declaration-line initializer (`int unsigned write_ptr = FIFO_DEPTH - 1;`) never persists across clock periods on its own?**
Correct. On its own it's a sim-only, time-0 value — not a clock-driven update. It's specifically the `write_ptr <= write_ptr + 1;` line inside `always_ff` that makes it a real, updating flip-flop; the initializer only ever matters for what the very first value looks like *in simulation*.

**Q: In `w <= w + 1`, where does the `w` on the RHS come from?**
The flip-flop's current stored output — whatever it was holding going into this edge (from the previous edge, or its reset/power-on state on the first one). This is exactly why nonblocking assignment is required in sequential logic: every RHS in an `always_ff` block evaluates off *pre-edge* values, and all assignments land simultaneously — modeling how real flip-flops in one clock domain all sample off each other's *old* values at the same instant, not off whatever another statement in the same block may have just written this edge.

**Q: Should `write_ptr` be decrementing instead of incrementing, given it starts at `FIFO_DEPTH-1` and checks `==0` for full?**
Directionally yes, *if* keeping that exact structure — but that structure is actually a different FIFO design (a single occupancy-counter: up on push, down on pop, full at `FIFO_DEPTH`, empty at 0) than the two-pointer approach from the concept doc, and it conflates two separate jobs into one variable: *where to write next* (needs to wrap `mod FIFO_DEPTH`) vs. *how full the FIFO is* (a separate count). Also surfaced a real out-of-bounds bug regardless of direction: `tx_fifo_reg[write_ptr+1]` indexes past the end of a `[FIFO_DEPTH-1:0]`-sized register. Landed on: two independent pointers (write/read), matching the concept doc — see below.

## Reset

**Q: Does an internal-only register (never a port) still need a reset?**
Yes — port-vs-internal is unrelated to whether something needs a defined starting value. Persistence (via `always_ff`) and defined-starting-value (via reset) are separate concerns. For *this* structure specifically: a dual-pointer FIFO has a real invariant — `write_ptr` and `read_ptr` must start in a known, mutually consistent relationship (both equal, i.e. empty) — otherwise `EMPTY`/`FULL` is comparing two independently-garbage power-on values before anything's even been pushed. Not a manufactured problem; reset is the standard way to actually address it. (FPGA toolchains can sometimes bake a declaration-line initializer into the bitstream as a real power-up value, but that doesn't port to ASIC, so an explicit reset is the right habit regardless.)

**Q: Why is `always_ff @(posedge clk or negedge rst_n)` asynchronous?**
Because the *sensitivity list* is what determines when the block executes at all. With `negedge rst_n` sitting in that list, a drop on `rst_n` triggers the block immediately, independent of the clock — could be mid-cycle. Maps to real hardware too: many flip-flop cells have a genuine dedicated async set/clear pin, separate from the clock/D-input path, that forces the output the instant it's asserted.

**Q: Is sync reset just `if (!rst_n)` inside a block with only `@(posedge clk)` listed?**
Yes. Since `rst_n` isn't in the sensitivity list, the block never runs just because `rst_n` changed — only on a clock edge. So reset only ever takes effect gated by the same clock edge as everything else, which is exactly why it's "synchronous." (Physically: sync reset is usually just a 2:1 mux on the flip-flop's D input, no special reset pin needed; async reset needs an actual dedicated pin and drags in its own reset-recovery timing concern.)

**Decision**: synchronous, active-low (`rst_n`), checked as the outermost condition in the same `always_ff` block, ahead of the push/pop logic.

## FIFO concept — depth, pointers, the extra bit

**Q: What is `FIFO_DEPTH`, precisely?**
A `parameter` (compile-time constant) — the count of byte-sized storage slots. Fixed per instantiation, logic written generically against it.

**Q: What are the write/read pointers, precisely, and what are they for?**
Two small counters holding an *index* into storage, not the data itself. Write pointer = slot the next push lands in (write, then increment). Read pointer = slot the next pop comes from (read, then increment). Both wrap at the end (ring buffer). What they're for: knowing where to write without clobbering unread data, where to read without re-reading stale data, and — by comparing them — whether the FIFO is empty or full.

**Q: Why do the pointers need one bit more than $\lceil\log_2(\text{FIFO\_DEPTH})\rceil$?**
Worked example, depth=8: addressing 8 slots needs exactly 3 bits ($2^3=8$). With *only* 3-bit pointers: start empty at read=write=0 (matches the actual reset value decided on below — the starting value itself is arbitrary to this argument; mod-8 wraparound returns to *whatever* value you started at after exactly 8 increments, regardless of what that value is). Push 8 bytes, write_ptr wraps 0→1→...→7→**0** again (mod-8 arithmetic) — identical to read_ptr. Empty and completely-full now produce the same comparison; 3-bit pointers can't tell "0 apart" from "one full lap (8) apart," since mod-8 makes 0 and 8 indistinguishable in 3 bits.

Fix: widen both pointers to 4 bits, but only use the bottom 3 (`ptr[2:0]`) as the actual memory address — let the full 4-bit value count to 15 before wrapping. Redo: read=0 (0000), push 8, write becomes 8 (1000). As 4-bit values, 0 ≠ 8 (distinguishable), but `8[2:0] = 0` (still addresses the right slot). Rule falls out naturally: **EMPTY** = pointers fully equal, all 4 bits. **FULL** = bottom 3 bits equal, but the extra bit differs.

**Q: Special meaning to the "multi-entry memory" framing?**
No hidden meaning — deliberately implementation-agnostic. §6.3 (referenced alongside it) is just the parameter table, not an implementation-choice section; nothing in the doc commits to flop-array vs. SRAM macro. At `FIFO_DEPTH=8` (or 16), a flip-flop array is the obvious practical choice — an SRAM primitive would be overkill — but the *concept* doesn't care which. Same object as the `logic [7:0] mem [0:FIFO_DEPTH-1]` shape, just described at the prose level instead of the RTL level.

**Q: Byte-sized slots — is a depth-16 FIFO really `[7:0][0:15]`-shaped? Is bit-per-slot ever normal instead?**
Yes to the shape: `logic [7:0] mem [0:15]` — first bracket is width-per-slot (8 bits = 1 byte), second is slot count. Bit-per-slot FIFOs exist elsewhere (bit-stuffing pipelines, internal serializer bookkeeping) but would be wrong *here* specifically — the rule is slot width should match the actual unit of data crossing that boundary. The CPU writes a whole byte to `TX_DATA` per transaction, so byte-wide slots are what matches; a bit-wide FIFO would force one push per bit, which doesn't correspond to any real transaction happening there.

**Q: Isn't UART bit-by-bit though — so is incoming FIFO data really a whole byte?**
Yes, and this is two different granularities that are easy to conflate. At the MMIO/CPU boundary: whole bytes (one `TX_DATA` write = one byte pushed). At the physical wire: one bit at a time, serially, over multiple baud periods (literally what "serial" means in UART). The FIFO lives on the byte-granular side; `tx_shift_register`/`rx_shift_register` are what actually do the bit-by-bit serialization.

**Q: Is `FULL`/`EMPTY` in all-caps a naming convention — I thought only parameters were?**
Half right. Looking at `mmio_register_bank.sv`'s own register-map comment: it's not just `parameter`s that are `ALL_CAPS_WITH_UNDERSCORES` in this project, documented STATUS/CTRL bit-field names are too (`TX_FIFO_FULL`, `BAUD_DIV`, etc.). `FULL`/`EMPTY` in prose refers to that register-map-level concept, not a mandate on RTL signal names — `tx_full` (lowercase, actual port name) is correct and doesn't conflict with anything. The two layers are allowed to differ: `tx_full` is the wire that ultimately feeds the documented `TX_FIFO_FULL` status bit.

**Q: Is this the same two-pointer pattern as LeetCode-style array problems?**
Yes — same pattern, running on a ring buffer in hardware instead of an array in software.

**Q: Should the pointers' initial state be 0, or the "front" of the queue (index 15 for depth=16)?**
Convention, not a technical requirement — but 0 is the practical default and "front=15" doesn't actually confer the advantage the queue metaphor suggests. A ring buffer has no fixed "front slot" once running — whichever slot `read_ptr` currently points to *is* the front, dynamically. The only real requirement is `write_ptr == read_ptr` at reset (whatever that shared value is), so EMPTY holds true initially. 0 wins on practical grounds: matches how everything else in the design resets, and reads far more intuitively in a waveform than needing to remember "15 means empty here."

**Q: Why not a single pointer — decrement on write, increment on read — instead of two?**
Traced through concretely (depth=16, start at 15): push A → pointer to 14 (A in some slot); push B → pointer to 13 (B in some slot); pop should return A (FIFO order) — but if pop just increments the *same* pointer back to 14, the next push lands in slot 14, which is where B (still unread) is sitting. Overwrites unread data. Root cause: write and pop happen at two genuinely different, independently-moving locations in the ring (the write frontier and the read frontier), except when the FIFO is empty or full. Collapsing them into one pointer conflates two different things and causes real corruption, not just an awkward description.

Real alternative to the extra-bit trick, though: keep both pointers separate and minimal-width (no extra bit), add a **third, separate occupancy counter** — up on push, down on pop, `FULL` at `FIFO_DEPTH`, `EMPTY` at 0. Same instinct, applied to a third signal instead of merged into the address pointers. Both designs (extra-bit-on-pointers vs. separate occupancy counter) are real and roughly equivalent in cost.

## Address routing / interconnect (applies to `mmio_register_bank.sv`, but conceptual)

**Q: CPU sends the full address to an "interconnect" (bus fabric — AXI is one concrete family of protocols implementing this role, not the general term itself), which routes to the peripheral whose base address matches. Then the peripheral routes to the specific component whose offset matches (e.g. the mmio bank), wiring in only the bits that component needs?**
Mostly right, one term swap: what crosses the bus is a **transaction** (address + control + data), not an "instruction" — instruction is a CPU-core/ISA concept describing what happened *inside* the core to produce the transaction. "Interconnect" is the correct general term for the routing fabric; AXI4/AXI4-Lite/APB/AHB/TileLink are concrete protocols implementing that role, not synonyms for it.

Correction on the second half: for *this* UART, there's no separate internal router module between the peripheral and the register bank. One register file owns all of CTRL/STATUS/TX_DATA/RX_DATA, so "route to whichever component's offset matches" **is** `mmio_register_bank`'s own `address[3:0] == 4'h00/...` comparisons — that if/case logic is the offset router, not a separate module. `uart_top`'s job is just handing the relevant address bits down (full 32-bit address, or a narrowed slice like `full_address[3:0]` if we take the port-narrowing lint fix). The interconnect has already confirmed "this belongs to the UART" before `uart_top` ever sees the transaction — nothing downstream re-checks the base address.

**Q: Why are CTRL/STATUS/TX_DATA/RX_DATA spaced 4 bytes apart (0x00/0x04/0x08/0x0C) instead of packed tighter?**
Direct consequence of two things this design already commits to: byte-addressing convention (addresses count individual bytes, standard across ARM/RISC-V/x86 and this design's own `[31:0]` address/data ports), and a 32-bit bus with no byte-enable/`wstrb` signals — nothing in the port list allows writing less than a full word. Every transaction grabs a whole aligned 4-byte chunk, so consecutive registers land 4 byte-addresses apart, not 1. (Low 2 bits of the address are always `00` for a valid access here — checking all of `address[3:0]` instead of just `address[3:2]` is a little redundant but not wrong.) Tighter packing would only make sense with a narrower bus or added byte-strobe logic for sub-word writes — not needed here since no register requires independent byte-level access within itself.

**Q: For RX_DATA read, `mmio_register_bank` needs to pulse `fifo`'s `pop` when `read_en` and the address match — but a module can't reach into another module's ports. Does `uart_top` need its own address-decode logic to drive `pop` directly, since it's the one instantiating both?**
Half right: `uart_top` is correctly identified as the only thing that can see both modules' ports at once (sibling modules never talk directly — always mediated by whatever instantiates both), but the address decode itself shouldn't move to `uart_top`. `mmio_register_bank` already owns that decode (it's the one module with `address`/`read_en` wired in, already doing the equivalent branching for CTRL/STATUS). Re-deciding "is this an RX_DATA access" a second time in `uart_top` would duplicate that logic in two places that must always agree — same problem `is_full` avoided by being factored into one shared wire instead of being written twice. Correct shape: `mmio_register_bank` gets a new **output** port (a pop-request pulse), decided by the same decode it already does; `uart_top` does no logic of its own here, just wires that output straight into `fifo`'s `pop` input.

This surfaced a real, live bug in the current draft: `pop` is declared as an **input** on `mmio_register_bank`, so `pop = '1;`/`pop = '0;` inside it fails with `%Error-ASSIGNIN` ("Assigning to input/const variable"). Needs to flip to an output — mmio decides *when* to pop, fifo owns *what* gets returned, top just wires the two together; RX_DATA read isn't "unrelated to mmio", mmio still owns the whole decision, just not the storage.

**Q: `fifo`'s `pop_data` is registered (updates the cycle *after* `pop` asserts), unlike CTRL's combinational read. Does RX_DATA need a wait/ready signal for the CPU, or should `pop_data` become combinational instead?**
Resolved: make `pop_data` combinational, don't add a wait/ready signal. `read_ptr` still has to stay in its own `always_ff` (a pointer is real state, has to persist across cycles) — the change is only to the *readout*, a continuous `assign pop_data = fifo_reg[read_ptr]` instead of a clocked, nonblocking one. This eliminates any lag concern rather than creating one: since `pop_data` is *defined as a function of* `read_ptr`, it can never desync from it — during the cycle `pop` is asserted, `read_ptr` hasn't advanced yet (only happens at the edge), so `pop_data` shows exactly the byte being requested for that whole cycle, matching CTRL's same-cycle read semantics exactly. It's the registered version that has the real lag (a full cycle behind), not the combinational one.

General rule of thumb this settles: writes *must* go through a clock edge to create new state — not a rule of thumb, definitional, no way around it. Reads *can* be combinational whenever the underlying storage supports it (plain flip-flops, small flip-flop-array FIFOs like this one) and should be, to avoid needless latency/protocol complexity. Reads are *not* guaranteed to be instant, though — real synchronous SRAM/block-RAM macros have an inherent one-cycle registered read latency (a technology constraint, not a design choice) — and *that's* when a wait/ready signal actually becomes necessary, only when a responder has genuine non-zero/variable latency it can't avoid. Don't add the signal preemptively; add it if and when that constraint actually shows up (e.g. a future SRAM-backed reuse of this `fifo` module).

**Q: A `pop`-gated combinational `pop_data` (`if (pop) ... ` with no else, or a ternary with no real fallback) throws "Latch inferred for signal 'pop_data'" — switch to `always_latch`?**
No — that would make the unwanted latch explicit/intentional rather than fixing the actual issue. This is a different failure mode than the "no `else` in an `always_ff` is fine" rule from early in this project: that rule is specifically about *clocked* blocks, where "no else" just means "hold on this edge," normal register behavior. Gating a *combinational* block on `pop` with no else means "sometimes don't drive this output," and combinational logic has no memory of its own to fall back on — the only way real hardware can honor that is a literal transparent latch (level-sensitive, not edge-triggered — while `pop` stayed high, any change to `fifo_reg[read_ptr]` would flow straight through), which is exactly what got inferred and exactly why it's undesirable here. The real fix is removing the `pop`-gating entirely: drive `pop_data` unconditionally from `fifo_reg[read_ptr]` at all times, no branches at all — then there's nothing left for the tool to warn about. A ternary with a concrete fallback (e.g. `'0`) avoids the latch too, but isn't equivalent to the ungated version — it'd only show the correct byte during the exact cycle `pop` is high and revert to the fallback the rest of the time, which is fragile and timing-dependent on exactly when the consumer samples it. The ungated version always shows a meaningful value (whatever's next to be popped), sampleable any time.

Once `pop_data` is a plain wire with no storage, resetting it (or asking whether it "holds" its last value) stops being a meaningful question — a reset value only applies to real registers. It won't "hold" the last popped byte between pops so much as continuously track `read_ptr`, which itself only moves forward on real pops.

**Q: Can the same RX_DATA-read transaction (`read_en` + address match) legitimately arrive on consecutive cycles? Does the design handle that correctly without remembering the previous cycle?**
Yes to both, and it's not by luck — it falls directly out of the design above. `pop_request` (mmio's decoded output) and `pop_data` are both purely combinational reactions to *current* signals; neither one carries any memory of a prior cycle. The only thing that does is `read_ptr`, in its own `always_ff`. So two consecutive cycles of the same-looking transaction just produce two independent, correctly-sequenced pops: cycle 1 pops byte N (via that cycle's fresh `pop_request`) and `read_ptr` advances at the edge; cycle 2's `pop_request` is decided fresh, with no awareness that cycle 1 happened, but `read_ptr` has already moved on, so `pop_data` now shows byte N+1. This is also *why* the earlier wait-signal question resolved the way it did: this only works cleanly because every register access here is defined as one complete, self-contained cycle, never a multi-cycle stall. If `read_en` staying high across multiple cycles were instead meant to represent one transaction still waiting on readiness (the wait-signal scenario that got ruled out), treating each cycle as an independent pop would double/triple-consume the FIFO for what was meant to be a single read. Ruling out the wait-state removes that ambiguity by construction, not by accident.

**Q: CTRL's read (`assign rdata = ... ? ctrl_reg : 'x;`) shows `'x` in the fallback branch — isn't `'x` supposed to be avoided since it's not synthesizable? What does `rdata` actually show?**
Different use of `'x` than the one worth avoiding. The caution applies to relying on `'x` to represent real hardware behavior you expect to carry meaning in simulation — e.g. an unreset register simulating as X to flag "not written yet," when real silicon actually powers up to some arbitrary concrete bit pattern, not a true unknown; that mismatch can mask real bugs. Using `'x` as a combinational mux's fallback branch is a different, well-established idiom: a "don't-care" hint telling the synthesis tool "you're free to optimize this however's cheapest," safe specifically because nothing ever legitimately reads `rdata` in that branch — the bus master already knows, from its own address, never to look at `rdata` unless it was actually reading CTRL. What synthesis actually produces for that branch is implementation-defined (often it just doesn't build separate logic at all, and effectively always drives `ctrl_reg`'s bits straight through) — it's guaranteed never to matter, not guaranteed to be any particular value.

**Q: Does `fifo`'s `pop_data` flow back into `mmio_register_bank`'s `rdata`, or does it bypass mmio and get exposed as its own top-level signal?**
Flows back into mmio, as a new input — not a bypass. The interconnect only ever sees one external read-data output from this peripheral; if `pop_data` were exposed as a separate top-level signal alongside mmio's own `rdata`, something would have to arbitrate between the two, which would duplicate the "who decides what `rdata` shows" job already established as belonging solely to `mmio_register_bank` (same "one decision-maker, top is pure wiring" principle from the interconnect/routing entry above). So `fifo`'s `pop_data` gets wired, through `uart_top`, into a new input on `mmio_register_bank`, and mmio's existing `rdata` selection just grows one more branch (RX_DATA match → that input, alongside CTRL match → `ctrl_reg`) — one more branch on an already-existing mux, not a second copy of anything.

This stays fully combinational end-to-end: module-instantiation wiring itself never adds a clock edge (a port-to-port connection is just a wire; registration only happens where an `always_ff` is explicitly written inside some module), and `fifo`'s `pop_data` plus mmio's `rdata` mux are both continuous assigns. So routing `pop_data` through mmio's `rdata` doesn't reintroduce the clock-edge delay that was the whole point of avoiding — it's one more combinational stage chained onto other combinational stages. ("Combinational" here still means real gate propagation delay exists physically, just small enough, by design, to settle well within one clock period — "same-cycle," not literally zero-time.)

One consequence worth being aware of, not something needing action: since `pop_data` is always combinationally available regardless of whether `pop` fires, *reading* it (observing its current value) and *popping* it (advancing `read_ptr`, actually consuming it) are genuinely two separate actions — reading it any number of times without asserting `pop` is harmless and idempotent, since nothing changes until the pulse does. That's the same "data validity and data value are separate signals" principle from the FIFO's own `empty`/`full` design, one layer further: "current value" and "consume-and-advance" are also separate concerns, not one. Nothing currently exposes a CPU-facing "peek without consuming" — `mmio`'s decode is planned to issue the pop-request pulse unconditionally on every RX_DATA read — but that's mmio's own choice, not a limitation of the wiring underneath it.

## TX_DATA write — the write-side mirror of RX_DATA's pop_request

**Q: A registered `push_request`/`push_data` (a draft `always_ff`, `<=` on both) — combined with `fifo`'s own registered write — would that be a 2-cycle delay before the byte's actually stored?**
Yes, exactly right — same category of problem as the read-side registered `pop_data`, mirrored to the write side. Registering `push_request`/`push_data` means the CPU's write on cycle 0 only becomes a valid `push_request`/`push_data` starting cycle 1 (one edge of latency just to get the decode into registered form), and `fifo`'s own `fifo_push` block — itself edge-triggered — only actually captures the byte into `fifo_reg` at the edge closing cycle 1, visible cycle 2. Two registered stages stacked in series, two cycles before anything's actually stored.

Making `push_request`/`push_data` combinational instead (plain `assign`s, no clocked block) removes the unnecessary stage: they reflect `write_en`/`wdata` instantly, so `fifo`'s own write logic — the only remaining registered stage, and the fundamentally necessary one, since creating new state always needs at least one real clock edge — captures the byte at the edge closing the *same* cycle the CPU wrote it. One cycle, not two. Same rule of thumb as before: writes must cross a clock edge to create state, but any *extra* registration before that unavoidable one is just needless latency.

**Q: `push_data`'s fallback branch (`write_en && ... ? wdata[7:0] : 'x`) — same `'x` question as CTRL's `rdata`?**
Yes, same legitimate "don't-care" use, mirrored to the write side. `push_request` is `'0` in that exact same branch (same condition drives both), and `fifo`'s `fifo_push` block only ever samples `push_data` when `push` is actually asserted (`if (push && !is_full)`) — so whatever `push_data` shows when `push_request` is low is never consumed by anything. Genuinely irrelevant, safe don't-care, not the "avoid X" case (that one's about X standing in for real hardware behavior, like an unreset register).

## `fifo.sv` — going from `tx_fifo` to a generic, shared module

**Q: If push always writes `tx_fifo_reg` and pop always reads `rx_fifo_reg`, shouldn't the module just be called `fifo`?**
Yes — confirmed once the ports became fully generic (`push`/`pop`/`full`/`empty`/`fifo_reg`, no `tx_`/`rx_` prefixes left anywhere but the module name). This fixed a real bug in the original draft: push and pop were writing/reading two *separate* arrays, so nothing pushed could ever come back out via pop — a FIFO needs push and pop sharing the *same* storage to be FIFO at all. Renamed module and file to `fifo`/`fifo.sv`, moved out of `rtl/tx_core/` to a neutral location (`rtl/fifo.sv`) since it's no longer TX-specific — meant to be instantiated twice (once per direction), not owned by one core.

**Q: Should `tx_fifo_pop`'s empty-check reference the registered `empty` signal directly instead of recomputing `write_ptr == read_ptr` inline? Same question for `full` inside the push block.**
No — recomputing inline is the *better* choice, not a stylistic non-difference. `empty`/`full` are registered signals (updated via nonblocking assignment in their own dedicated blocks), so they always lag one cycle behind the raw pointers. If push/pop used the registered versions for their own decisions, a push or pop attempted the cycle right after the FIFO's real state changed (e.g. right after a pop frees space) would see last cycle's stale value and could incorrectly reject something that should've succeeded. The direct inline comparison uses the same-cycle pointer values, avoiding that lag — keep it, don't switch to referencing the registered outputs.

**Q: Can the repeated full-condition expression (needed in both `fifo_full` and the push block) be factored out without duplicating it *and* without paying for an extra register?**
Yes — a plain combinational `logic` signal driven by a continuous `assign` (not inside `always_ff`) does both at once: it's a wire, not a flip-flop, so there's no storage/no clock-cycle delay (avoids reintroducing the staleness problem above), and since exactly one thing drives it, there's only one copy of that comparator logic at synthesis — every consumer just reads the same wire. A `function` called from multiple places would *not* guarantee the same sharing — HDL functions behave more like inlined text substitution at each call site, so most tools would duplicate the logic there too, relying on their own optimizer to notice and merge it after the fact (usually works for something this simple, but not structurally guaranteed the way a shared wire is).

**Q: Does `fifo_reg <= '{default: '0}` on reset (clearing the whole array) matter, now that this is a generic reusable module?**
Not functionally required — same reasoning as `pop_data`'s reset (see mmio section above): nothing ever legitimately reads a `fifo_reg` slot that hasn't been genuinely pushed to, so there's no correctness need to clear it. Worth removing, though, for a reason specific to this array being large and now generic: a real SRAM/block-RAM macro (which a much deeper future reuse of this module might want, for area efficiency) physically can't bulk-clear its entire contents in one cycle the way flip-flops with reset logic can — SRAM's density comes precisely from *not* giving each tiny cell its own independent control logic, which is what a per-cell reset would require. Requiring a one-cycle full-array reset would force flip-flop-array synthesis even where SRAM would be more efficient at a larger depth, or fail outright against a real memory compiler. Not a problem at `FIFO_DEPTH=16` today (a flip-flop array is the right and only sensible choice at that size regardless) — worth removing now anyway for consistency and to not leave a landmine for a future deeper reuse. Removing it also has zero downside beyond losing clean `X`-free waveforms pre-first-write in sim, and actually *saves* area (no reset wiring fanned out to every cell). Same applies to `pop_data`'s reset, for the same consistency reason.

## `baud_generator` — clock divider, oversampling, and why 16

**Q: The divider concept (count to D, pulse, reset) already makes sense — where does "16 ticks per bit period" actually come from? Is tick rate the same thing as baud rate?**
No — treating those as the same thing is exactly the trap. Four distinct quantities, easy to conflate into two: **baud rate** (bits/second, what you actually want, e.g. $115200$ — for plain UART, "baud" and "bits per second" are literally the same number, since each symbol is one bit); **bit period** $= 1/\text{baud rate}$ (how long one bit sits on the wire); **tick rate** (how often `baud_generator` actually pulses) and **D** (the counter's target, $D = f_{clk}/\text{tick rate}$, always — nothing more to the divider mechanism than that, ever).

The mistake is assuming tick rate = baud rate. In this design it doesn't — $\text{tick rate} = 16 \times \text{baud rate}$, deliberately. A naive, non-oversampled design *would* set tick rate = baud rate (one pulse exactly at each bit boundary, and that pulse itself means "shift the next bit"), and in that version, $D = f_{clk}/\text{baud rate}$ really would give one tick per bit period. This design instead picks a **smaller** D — $D = f_{clk} / (16 \times \text{baud rate})$ — so the *same* single-pulse-per-cycle counter simply pulses 16× more often. There's no separate "ticks how many times per count-to-D" — it's always exactly one pulse per cycle; the only thing that changes is what number D itself is.

**Q: What do "edge"/"boundary"/"middle"/"center"/"sample"/"oversample" actually mean — a bit is one value, how does a single value have a center?**
The reframe that resolves this: a bit, as an abstract 0/1 value, has no middle — but a bit as it *physically exists on the wire* isn't just a value, it's a voltage **held constant for a stretch of time** (the bit period). That stretch has a beginning, an end, and everything between. "Edge"/"boundary" = the transition moment where the voltage is actively switching to a new bit's level — physically noisy/unsettled for a brief real moment (transistor settling time, reflections), not instantaneous the way an idealized abstract bit would be. "Middle"/"center" = the point in *time* within that stretch maximally far from both the incoming and outgoing edges — safest to read, since transition noise has fully died down and it gives the most slack against clock-drift error in either direction. "Sample"/"sampling" = checking the voltage at one specific instant and recording it — a receiver only ever knows a signal's value at the instants it explicitly checks, nothing in between. "Oversampling" = taking more samples across one bit than the bare minimum (one) needed, specifically so you can *choose* whichever sample lands closest to that safe middle, instead of being stuck with whatever single sample you got.

**Q: What does "8N1" (and the like) actually mean?**
Shorthand for frame configuration: `<data bits><parity><stop bits>`. **8N1** = 8 data bits, No parity, 1 stop bit — the overwhelming default, this module's own base target, 10 bit-periods total (1 start + 8 data + 1 stop). Not unique to this design — standard UART terminology everywhere. Other real configs from this doc's own table: **8E1** (8 data, Even parity, 1 stop, 11 bit-periods — common on RS-485/industrial links wanting basic error detection), **8N2** (8 data, no parity, 2 stop bits, 11 bit-periods — older hardware needing more settling time before the next start bit), **7E1** (7 data, Even parity, 1 stop, 10 bit-periods — legacy 7-bit-ASCII-era links).

**Q: What is "clock drift," concretely — why does middle-of-bit sampling counter it?**
Root cause: UART has no shared clock wire at all (unlike SPI/I2C, which send an explicit clock alongside data) — TX and RX each run their own independent, free-running clock, synchronized only by both sides being separately configured to the same nominal baud rate beforehand. No real oscillator is perfectly accurate — every crystal/RC oscillator has some manufacturing tolerance, so two devices both configured for "115200 baud" are actually running at very slightly different real bit rates under the hood.

The *only* instant the two sides are perfectly synchronized is the start bit's falling edge — the one shared reference point a receiver gets. From there on, the receiver counts off what it believes are bit-period-length intervals using its own slightly-off clock, and that guess gets progressively less accurate the further it is from the start bit — a small per-bit error that *accumulates* with distance from the last sync point, rather than staying fixed. That accumulating error is "drift."

Since the error grows with distance from the start bit, the *last* bit in a frame carries the worst-case accumulated drift — for 8N1, the receiver samples that last bit at $9.5$ bit-periods after the start edge (start bit + 8 data bits, sampling the 9th bit's middle). If the two ends' baud rates differ by a fractional error $\varepsilon$, the sample point has drifted by $\varepsilon \times 9.5$ bit-periods by then, and stays inside the correct bit only as long as that's under half a bit period:
$$0.5 = \varepsilon \times 9.5 \implies \varepsilon \approx 5.26\%$$
This is the *theoretical* ceiling — assumes perfect centering, nothing else uncertain. Real designs budget in the receiver's own oversampling granularity and both ends drifting in opposite directions simultaneously, so practical designs target well under half of this, typically $\le 2\%$ — $5.26\%$ is a hard ceiling, not something to design toward.

This is exactly what middle-of-bit sampling buys: sampling right at an edge gives zero margin for any drift at all, since even a tiny mismatch risks catching the wrong bit; sampling at the middle gives up to half a bit period of slack before accumulated drift actually causes a misread. 16× oversampling with majority voting is what turns "sample near the middle" from a vague intention into an actual, buildable mechanism.

**Q: Why 16 specifically — what else could it have been?**
Directly comparable against other real oversampling factors, more ticks = finer-grained candidate sampling instants = closer to the true middle = more margin against drift/noise:
```
1x  (naive):  one tick, right on the edge -- no choice at all, worst possible spot
4x:           4 candidate instants -- coarse
8x:           8 candidate instants -- finer (STM32F4's alternative)
16x:          16 candidate instants, majority-voted at 7/8/9 -- finest of the three, this design's choice
```
The real cost of going higher isn't the extra counter logic (a 3-bit vs. 4-bit counter is trivial) — it's on the other side of $D = f_{clk}/(N \times \text{baud})$: for a fixed system clock, D can't go below some practical minimum, so a *higher* N caps the *maximum achievable baud rate* on that clock. STM32F4 supporting both 8× and 16× is exactly this trade-off made explicit: 16× for more margin, 8× for a higher achievable top-end baud rate at the cost of coarser centering.

**Q: What value will `BAUD_DIV` actually be, and should this design use a real-silicon-style fractional divider instead of a plain integer one?**
$$\text{BAUD\_DIV} = \frac{f_{clk}}{16 \times \text{baud rate}}$$
A runtime-configured `CTRL[31:16]` field, not a fixed constant. At this module's own stated anchor ($115200$ baud, 8N1, $f_{clk} = 70\text{ MHz}$, this core's own fabric clock):
$$\text{BAUD\_DIV} = \frac{70{,}000{,}000}{16 \times 115{,}200} \approx 37.977 \implies 38$$
Checked the resulting error directly rather than trusting the doc's "comfortably close enough" claim at face value: `BAUD_DIV`=$38$ gives an actual baud rate of $\approx 115{,}131.6$ instead of $115{,}200$ — about **$0.059\%$ error**, comfortably under even the $\le 2\%$ *practical* target from the clock-drift derivation above (let alone the $5.26\%$ theoretical ceiling). The claim holds up.

Real silicon (STM32 `USART1`, per RM0090) uses a *fractional* divider instead:
$$\text{baud} = \frac{f_{PCLK2}}{16 \times \text{USARTDIV}}, \qquad \text{USARTDIV} = \text{Mantissa} + \frac{\text{Fraction}}{16}$$
Worked example at $115200$ baud, $f_{PCLK2} = 84\text{ MHz}$: $\text{USARTDIV} = \frac{84{,}000{,}000}{16 \times 115{,}200} \approx 45.57 \implies \text{Mantissa}=45,\ \text{Fraction}=\text{round}(0.57\times16)=9$. The fractional stage works by *dithering* the count length — counting to Mantissa most of the time, occasionally one cycle longer — so the *average* tick rate lands on the fractional target even though any single tick period is still a whole number of cycles.

The doc's own spec defaults to the plain integer counter for this design ("comfortably close enough" at this specific clock/baud combination) — but decided to build the fractional route instead, matching real silicon, rather than the doc's simpler default.

## `tx_shift_register`/`tx_fsm` — shift timing, and a real bug in `tx_start_pulse`'s trigger condition

**Q: `tx_shift_register`'s doc entry says "one bit per detected tick" — literally every raw (1-of-16) tick, or once per detected bit period?**
Once per detected *bit-period* tick — the doc's own one-line "what it is" summary is loose/imprecise here, and disagrees with its own more careful bullets a few lines down: `tx_shift_register`'s "what it does"/"when it acts" both say "on a **detected bit-period tick**," and `tx_fsm`'s own flow says shift-enable asserts "**once per bit period**." Shifting on every raw tick would move the register 16 positions during a single actual bit period on the wire, which doesn't correspond to anything real — worth trusting the detailed bullets over one-line summaries when a doc's own wording disagrees with itself like this.

**Q: The doc says `tx_start_pulse` fires "if `tx_fsm` is currently idle and `tx_fifo` was empty *before this push*." Shouldn't the real trigger just be "fifo has entries AND fsm is idle," continuously evaluated, so already-queued bytes actually get drained one after another?**
Yes — this is a real bug in the doc's stated condition, not a misreading, confirmed by checking `tx_fsm`'s own state transition table directly: `TX_STOP` always returns to `TX_IDLE` (no conditional/autonomous continuation), and `TX_IDLE`'s *only* exit is `tx_start_pulse`. If the pulse is generated *only* by "fifo was empty before this specific push" (tied to a write event), trace a 3-byte burst: byte 1's push genuinely catches the fifo empty → pulses correctly, transmits. Bytes 2 and 3 are pushed while the fifo already has byte 1 queued → "empty before this push" is false, no pulse for them. And once `tx_fsm` finishes byte 1 and returns to `TX_IDLE`, nothing re-evaluates anything, since no new write is happening at that instant. Bytes 2 and 3 would sit in `tx_fifo` forever — stranding every queued byte except the first in any burst, defeating the entire point of buffering ahead of time.

The underlying premise settles it: a `TX_DATA` write is unconditionally "send this as soon as possible" — there's no other reason that register exists, no separate "queue but don't send yet" semantic anywhere in real UART hardware. That extends to every byte already queued too, not just the one just written. The correct trigger is a continuously-evaluated condition — fifo not empty AND fsm idle — independent of whether a write is currently occurring, so the instant `tx_fsm` lands back in `TX_IDLE` mid-burst, the condition is still true and it keeps draining until the fifo genuinely empties.

Confirmed against real hardware, not just internal doc-consistency: STM32 USART's `TXE`/FIFO-not-full flag drives an autonomous refill — the shift engine continuously checks "queued byte + currently idle" and loads the next one with zero further software involvement, completely independent of new writes. The classic 16550 UART's TX FIFO works the same way. Both have worked this way for decades — the doc's push-triggered-only wording is the outlier here, not real hardware.

Implementation nuance to keep in mind later: the doc calls `tx_start_pulse` a one-cycle pulse, but "not empty AND idle" as a plain combinational condition would stay *high* for as long as both hold, not blip once. Probably harmless for `tx_fsm` itself, since it only samples the signal while actually sitting in `TX_IDLE` and stops caring the instant it leaves — but worth double-checking if anything else later expects a genuine one-shot pulse rather than a held level.

## `tx_fsm.sv`/`tx_shift_reg.sv` — clocking discipline and register correctness

**Q: First drafts had `always_ff @(posedge tick)` and `always_ff @(posedge bit_period_complete)` — why was that wrong, given `tick`/`bit_period_complete` genuinely only need to matter some of the time?**
Because neither signal is a real clock — both are combinationally-derived pulses, and `posedge <anything>` in a sensitivity list treats whatever's there *as* a clock, gated/derived from the real one. That's a real anti-pattern (glitch-prone, breaks static timing analysis, creates a second clock domain nothing else in the design has). The fix isn't "find the right signal to clock off of" — it's that every `always_ff` in this module clocks on `posedge clk`, same as everything else, and `tick`/`bit_period_complete` become *conditions checked inside the block* (an enable), not sensitivity-list triggers. This is also why the original code tripped Verilator's `SYNCASYNCNET` warning on `rst_n`: the (correctly-clocked) state register used `posedge clk or negedge rst_n`, while the other two blocks checked `!rst_n` synchronously with no `clk` in their sensitivity list at all — same reset signal, two incompatible styles, purely a symptom of the derived-clock bug.

**Q: `tx_shift_reg`'s first draft used `assign shift_register = shift_enable ? shift_register >> 1 : load_enable ? tx_fifo_pop_data : '0;` and Verilator flagged `UNOPTFLAT` (circular combinational logic) — why, and why does it specifically need `always_ff` rather than just restructuring the `assign`?**
`assign` is a continuous, memory-less combinational driver — it has no notion of "current value" versus "next value," it just has to resolve instantly from its inputs. Feeding it its own output as an input is a genuine circular dependency: to know the output, it needs the output, which Verilator can't flatten into an orderable network (that's what `UNOPTFLAT` means — not a subtle math error, a real unresolvable loop). A register only makes sense — "hold this value until told to change it" — inside a clocked (`always_ff @(posedge clk)`) process, where the clock edge itself is what cleanly separates "current" from "next." Referencing your own current value to compute the next one is completely normal there (it's exactly what `state <= next_state` already does for the FSM's own state register); it's only illegal-in-spirit as a plain `assign`, because `assign` was never a storage element to begin with.

**Q: Sync or async reset — is "matches `fifo.sv`" the actual reasoning, or is there a general rule for when to reach for each?**
The general criterion: **async reset** forces known state immediately, independent of whether `clk` is even toggling — needed at a true reset-entry point (e.g. right where a chip-level reset first lands), where the clock/PLL might not be stable yet. The catch is that async reset needs its *de-assertion* synchronized to `clk` (the standard "assert async, release sync" pattern via a reset synchronizer) — a raw async reset wired straight from an external pin with no synchronizer risks reset-removal metastability if `rst_n` happens to release right at a clock edge. **Sync reset** only takes effect on a clock edge — no removal-timing hazard, no synchronizer needed, but it requires `clk` to actually be running to ever reach the reset value, and adds one more term into every flop's input mux. `tx_fsm`/`tx_shift_reg` (like `fifo.sv`) are downstream, single-clock-domain modules consuming an already-arriving `rst_n`, not the place a chip's real reset first enters — so sync is the right (simpler) choice for *this class* of module specifically, not a blanket "always use sync" rule.

**Q: `tx_shift_reg`'s `shift_register <= tx_fifo_pop_data` (on `load_enable`) and `fifo`'s own `read_ptr <= read_ptr + 1` (on `fifo_ctrl.pop`) both fire on the same clock edge, in two different modules — can that race, e.g. capturing the wrong byte or missing one?**
No, and non-blocking assignment (`<=`) is specifically why. The rule: every RHS of every non-blocking assignment across *every* `always_ff` block reacting to a given clock edge gets evaluated using the values as they stood immediately *before* that edge — none of them can see any other block's same-edge update while computing their own new value. So at the edge where `load_enable`/`tx_fifo_pop` is high, `tx_fifo_pop_data` (combinationally `fifo_reg[read_ptr]`) resolves against the pre-edge `read_ptr`, completely independent of `fifo`'s `read_ptr <= read_ptr + 1` being evaluated (against that same pre-edge `read_ptr`) in that identical instant. Both results commit together: `shift_register` gets the byte that was actually at the old `read_ptr`, and `read_ptr` advances — no window where either module could observe the other's already-advanced state. This is also the real reason `<=` (not blocking `=`) is mandatory in `always_ff`: with blocking assignment, the order two *different* blocks happen to execute in on the same edge would actually matter, and this exact scenario would become a genuine race depending on simulator/synthesis scheduling.

## `state_output` block — why `default:` still matters alongside pre-case defaults

**Q: `state_output` sets `tx`/`tx_shift_enable` to safe values *before* the `case`, so every branch already has a fallback. Isn't the `default: tx = '1';` inside the `case` itself now redundant?**
Redundant for the *named* states, yes — an unmatched case there would just fall through to the pre-case value anyway. It's not redundant for what it's actually guarding against: `state` is a `logic [2:0]` under the hood, which can hold 8 possible bit patterns, but only 5 are named enum values. The other 3 are encodings nothing in the design *intends* to reach — but nothing stops the hardware from landing there anyway (a register isn't guaranteed to power up at a named value before reset propagates, and on real silicon a glitch or single-event upset can flip `state` into an unnamed encoding). Pre-case defaults solve latch inference for the states you *do* name; `default:` is the deliberate answer to "what does this FSM do if it's ever wrong" — a different problem, not the same one twice. Given the pre-case defaults already hold the values you'd want in that recovery case anyway (idle-safe: `tx = '1'`, don't shift), `default:` doesn't need to restate every signal — only ones that must differ from the pre-case value, which here is none; `default: ;` would behave identically. Kept the explicit `tx = '1'` restatement anyway, for readability — it documents *at the branch* that idle-safe was a deliberate recovery choice, not an oversight, rather than relying on a reader to connect an empty branch back to the pre-case defaults above.

## `uart_pkg.sv` — `parity_e`/`stop_bits_e` placement and enum design

**Q: `parity_e`/`stop_bits_e` used to be raw magic-number comparisons local to `mmio_register_bank.sv`; why promote them into `uart_pkg` as real enums, and specifically — why is `stop_bits_e` a 1-bit enum (`ONE_STOP_BIT=0, TWO_STOP_BITS=1`) instead of 2-bit with the literal counts (`ONE_STOP_BIT=1, TWO_STOP_BITS=2`)?**
Promoting them gives every module a single shared, named vocabulary instead of re-deriving/re-guessing bit patterns per file (same reasoning `DATA_BITS`/`FIFO_DEPTH` already got). The width choice is the more interesting part: a 2-bit-wide enum with literal `=1`/`=2` values would still let `.STOP_BITS(3)` through via an explicit cast (most tools don't hard-reject an out-of-range cast into an enum, only a bare untyped literal) — real but not airtight protection, and 2 of its 4 possible encodings would be reachable-but-meaningless. A 1-bit-wide enum with arbitrary (not literal-count) encoding has *zero* invalid states by construction — every possible value of a 1-bit field is legal, nothing left to enforce. That's viable here specifically because `STOP_BITS` is a `parameter` — fixed at elaboration by whoever instantiates the core, not a live runtime register a glitch or bad bus write could ever corrupt — so there's no defensive-recovery question to weigh (unlike `tx_state_e`, a real runtime register, where the `default:` case above earns its keep). The cost: the encoding no longer equals the literal stop-bit count, so anything consuming `STOP_BITS` arithmetically (the way `DATA_BITS` drives `TX_DATA`'s bit-count comparison) will need a `case`/branch instead of direct math — a real tradeoff, made deliberately in exchange for the width being airtight.

## `mmio_register_bank.sv` — why it doesn't `import tx_pkg::tx_state_e`

**Q: Now that `lint-all` sorts packages first, compile order would let `mmio_register_bank` `import tx_pkg::*` and read `tx_state_e` directly. Is that actually illegal, or just avoided by choice?**
Legal, not illegal — satisfying compile order is sufficient for the import itself to work. Avoided anyway, and deliberately: `tx_fsm`'s internal state enum is an implementation detail of *that* module, not a public interface. If `mmio_register_bank` (or anything else) started reading `tx_state_e` directly, `tx_fsm` could never change its own internal encoding, add a state, or restructure its FSM without also auditing every other module that peeked inside it — the opposite of encapsulation. `tx_fsm` already exposes exactly the abstraction other modules should need: `tx_busy` (a plain boolean matching the documented STATUS register bit), derived internally as `state != TX_IDLE`. Anything that needs to know "is a transmission in progress" should consume `tx_busy`, not import the enum and compare against `TX_IDLE` itself — same principle as any module boundary: expose the minimum abstract signal a caller actually needs, keep the internal representation free to change.
